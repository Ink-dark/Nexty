# ADR: `url` 改为 nexty-network 直依赖（resolve 特性不再借 reqwest）

- 日期：2026-10-31
- 状态：已采纳
- 背景：`nexty-network` 的 `resolve` 特性原先通过 `resolve = ["dep:reqwest"]`
  拿 reqwest 再导出的 `Url` 类型，导致「只想要 URL 解析」的下游被迫拉入整个
  reqwest + TLS 栈；同时 K3 导航轮（goal T5）需要文档 URL 的解析 / 拼接门面，
  依赖类型不得外泄的硬规则也要求自有封装。导航与网络完备轮（network
  0.1.5 → 0.1.6）T1 落地。

## 候选

| 候选 | 许可证 | 结论 |
| --- | --- | --- |
| `url` 2.5.8 直依赖 | MIT OR Apache-2.0 | **采纳**。WHATWG URL Standard 的官方 Rust 实现（Servo 出品，Chrome/Firefox 生态共用），本仓库硬规则「WHATWG 规范 > WPT > 成熟 crate > 自研」下的 obviously 正确选择；且已是依赖树成员（reqwest 传递依赖），直依赖化**零新增包** |
| 继续借 reqwest 的 `Url` | MIT OR Apache-2.0 | 否决：resolve 特性拖整个 reqwest + rustls + tokio 运行时依赖面，与「每层最小依赖足迹」相悖；reqwest 也只是 re-export `url::Url`，不提供额外解析能力 |
| 自研 URL 解析 | — | 否决：WHATWG basic URL parsing（IDNA、路径归一、query/fragment 语义）是典型的「有成熟轮子不自己造」，自研违反 AGENTS.md 选型优先级 |

## 决策

1. **依赖接线**：`resolve = ["dep:url"]`，不再隐含 reqwest；`url = { version =
   "2.5.8", optional = true }`（锁内已有 2.5.8，不引入版本漂移）。
2. **API 面**：`pub fn resolve(base, target)` 签名不变（`String` 进出，
   `NetworkError` 错误），既有回环测试与 chrome 调用点零改动。
3. **最小封装**：新增自有类型 `nexty_network::Url`，只暴露 `parse` /
   `join` / `as_str` 三个操作（本轮与 T5 所需），`url::Url` 字段私有，不外泄
   依赖类型（硬规则）。`join("")` 显式短路返回自身，与 `resolve` 的空串语义
   一致（opaque scheme 的 `join("")` 在 url crate 中会失败）。
4. **能力边界**：不暴露 scheme / host / path 等访问器，不做序列化构造——
   下游确有需求时再加（Style Conventions：别为未来需求加参数）。

## 许可证与依赖面

- `url` 及其传递依赖（`idna` / `form_urlencoded` / `percent-encoding`，MIT OR
  Apache-2.0）全部在 `deny.toml` 白名单内；`cargo tree -p nexty-network
  --no-default-features --features resolve` 已断言依赖树无 reqwest。
- 由于 `url` / `encoding_rs` 本就在 Cargo.lock（reqwest 传递），本轮直依赖化
  不新增任何包，`cargo deny check` 与 `cargo about generate` 产出无实质变化
  （批次收口时按流程重跑并重新注入）。

## 验证

- `cargo check -p nexty-network --no-default-features --features resolve` 编译
  通过零 warning；`cargo tree` 断言无 reqwest（见上）。
- resolve 既有回环测试（`resolve_handles_relative_paths` 等 4 条）在
  resolve-only 配置下不变绿；新增 `Url` 封装单测 3 条（parse/join/as_str、
  空 join、opaque base）。
